# Architecture

This describes what Eclipse does today. Each module's docstring has the details.

## Pipeline

```text
capture ──> waiting to scan ──> text layer ──> compositor ──> delay buffer ──> output gate ──> virtual camera ──> OBS
                  │                  ▲                                               ▲
                  └──> OCR workers ──┘ (Apple OCR only)                   panel and panic key
```

Every frame is scanned by the text layer and drawn by the compositor before the delay buffer hands it to the output. Output never receives a raw frame, so there is no path for an unscanned frame to go out. If a scan fails or runs out of time, the last safe frame stays up.

## Modules

| Module | What it does |
| --- | --- |
| `capture/` | On macOS, `sck.py` uses ScreenCaptureKit, which hands over each new picture and sends nothing while the screen is still. If it can't start or stops mid-run, `preferred.py` falls back to polling with `mss` (`screen.py`). `webcam.py` reads a camera through OpenCV (`--webcam INDEX`) and always uses RapidOCR. Pick the real camera, not OBS Virtual Camera, or the output loops back in. If the camera stops sending frames, the run stops. `clip.py` reads a recorded clip, and `pattern.py` draws a moving test pattern with a fake secret. |
| `text_detect/` | Reads text with OCR and finds secrets in it. See [Text layer](#text-layer). |
| `compositor/compositor.py` | Draws a solid black box over each detection, padded by at least 10 px. A `held` detection is filled from the last safe picture it drew instead, so a pane not yet checked shows what already went out there, not black. If the scan failed, it returns the last safe frame instead. It keeps no boxes between frames: the text layer reports everything to cover on every frame. |
| `compositor/delay.py` | Runs capture, scanning and output side by side. Output sends each frame `--delay` seconds (1.0 by default) after capture, so a slow scan uses up some of the delay instead of freezing the picture. A frame that can't be scanned in time is dropped. With `--look-ahead` (0.3 s by default, at most 30% of the delay), a scanned frame waits that long before the compositor draws it, so the text layer can use the frames scanned after it. |
| `compositor/gate.py` | The last check before a picture leaves. Panic, resume and settings changes land here, so they take effect at the output however far behind the scanner is. Panic blacks out everything, including frames already in the buffer. After resume, nothing captured before it is shown. A setting that hides more blocks anything scanned under the old setting. On shutdown the gate closes and the last frame sent is black. |
| `output/virtual_cam.py` | Fits each frame to the camera size and sends it to OBS Virtual Camera on a fixed 60 Hz grid. Each frame is prepared before its tick and stamped with the tick, not with when it left. On macOS `obs_mac_camera.py` writes UYVY frames straight to OBS's camera extension so it can set that stamp. Elsewhere `pyvirtualcam` sends them and stamps them as they leave. OBS paces by the stamps only when the Video Capture Device has Use Buffering ticked. Without it, OBS shows whatever arrived last at each of its own ticks, and frames landing near a tick are doubled or skipped. |
| `panel/` | A local page at http://127.0.0.1:8000 with category toggles, a keyword list, a catch log, and panic and resume buttons. Keywords are saved in `~/.eclipse/config.json`. The catch log records categories and times only, never screen text. `hotkey.py` adds a global panic key, Control+Option+B on a Mac. |
| `types.py` | `Frame`, `Detection` and `Rendered`, the shared contract between modules. |
| `platform.py` | The only module that checks which OS it is on: permission checks, ScreenCaptureKit and Retina settings, the camera driver (Media Foundation on Windows), peak memory, and Apple's OCR. |
| `main.py` | Wires the pipeline and writes numbers to `eclipse-run.log` every 2 seconds. Never screen text. |

## Text layer

`Detector` in `text_detect/detection.py` handles each frame in order:

1. It finds the rows that changed and reads only those. Past 60% of the screen, it reads the whole frame.
2. When an area scrolls vertically, it moves the text it already knows instead of reading it again. Rows scrolling into view stay black until they've been read, but only where they show something: background-coloured pixels can't hide anything, so the black covers each incoming line's text, not the pane's width. With OCR workers, incoming rows are read as soon as more than the cut line has come in. Without them, once 96 have come in, or as soon as a whole line has come in past the one the edge cuts (at most every other frame). The line the edge cuts through is measured from the pixels: it runs from the edge to the first blank rows, and is nothing when the edge falls between lines. Columns inked in nearly every row, such as the pane's border, the pane beside it or a scroll bar, are left out of that measure: counted as ink, they left no blank row, so three lines at the edge stayed black and each line blinked black for a third of a second as it scrolled in. It stays unread until it is whole.
   A window dragged straight up or down looks like a scroll at first. What it uncovers stays still in the next frame, though, while text scrolling in moves on with the scroll, so from then on it is followed as a window move: nothing is held black, and what it uncovers is read where it shows.
   While a pane scrolls, and after it stops until its window moves, a cover whose text the pane's top or bottom edge cuts through isn't dropped by a read that finds nothing there: no read can see a cut line whole.
   If something else changes at the same time, such as a live OBS preview beside the window, it finds the columns that scrolled and follows those alone. Within what it follows, the scrolling area is the pane whose pixels the shift explains, not every pixel that changed. Other things change in the same frames, like OBS's preview of the screen or an audio meter, and would otherwise stretch the area, so the black incoming rows landed on them instead of on the pane's edge. Blocks of pixels the shift explains are joined across blank lines but not across wide gaps to the side. Groups beside the pane join it only if the shift explains them almost exactly. When the whole change gives no shift, each part kept apart by unchanged columns is tried alone.
   Rows scrolling in are only black while that frame waits to be drawn, though. `text_detect/incoming.py` follows each frame's black rows through the frames scanned after it. Every step must reproduce their pixels exactly: unchanged, or moved by a scroll whose shift explains every pixel of the pane. Once a later frame has read them and they're not part of a line its pane's edge cuts, the frame goes out with those rows as they are, plus that later frame's covers moved back by the scroll and kept inside the pane. A later frame at rest also clears rows it shows as read, cut line included, as frames at rest always show it: earlier frames then show the same pixels or fewer, slightly sooner. Rows still unresolved don't go black: the pane is held, showing the last safe picture of it, so a scroll can pause briefly or step instead. This shows nothing OCR found. Rows where the read found text that looks like a secret (an @, five or more digits, or a long token mixing digits or cases) but no rule matched stay black, since OCR may have misread a real one.
   When a window is dragged in any direction, it finds the shift that makes the window's pixels match the previous frame exactly and moves known text and covers by it. Text moves only if every pixel of its new place matches. Anything else, and every pixel the shift doesn't explain, is read again. A cover moved this way gets no extra margin while it waits for a read, so it doesn't swell as text slides under another window's edge. While a drag carries on, it's looked for only around where the dragged window landed last frame, so changes elsewhere, like a reply streaming into another window, neither cost time nor outvote its pixels. The shifts around the one expected are checked first: last frame's shift per captured frame, times the captures since, as frames dropped while the scanner was busy stretch a drag, and where the drag is heading. If none fits, one shift search runs over that region alone. The best candidate then steps to any neighbouring shift that matches better, so a shift a pixel short of the real one is never taken. Before any of this, other big changes on screen are checked for a scroll: a pane scrolling in a second window comes first, as following it is what keeps it covered. A straight up-or-down shift isn't taken this way, as it may be a scroll. When the drag stops, nothing fits, and everything is tried as usual.
   Changes are split into separate areas first. A quick scroll check runs across all of them; then each area big enough to be a pane or a window is tried alone, largest first, so a note scrolling beside OBS's live preview is still followed. An area whose changes go unexplained three frames running, like that preview, is left out of these checks and retried every 10 frames. Its changes are still read every frame. When only small things change, like the cursor, just the quick scroll check runs. This keeps the diff stage within a 60 fps frame with the preview on screen.
3. It puts the words it read into lines, then runs the rules in `rules.py` on each line: email, phone, 2FA code, API key or password, card number and the user's keywords.
   - **Lines.** Words on a row join when their gap is under twice the row's usual text height, not the height of either word's own box, so a few-pixel-tall `=` box doesn't split `password` from its value. Words farther apart, as in two windows side by side, stay separate. There's one exception: if the first word ends in a label and the pixels between show ink OCR didn't read, they still join, up to four text heights apart. Vision often drops the `=` in `password = hunter2`. Words a few pixels apart are one token Vision split, like long hex. Overlapping words are two readings of the same place and are never joined into one token. In a line that names a secret, any wide gap with ink in it counts as punctuation OCR dropped, so a value ends there: Vision can read `{"password": "s3cr3t pass", "user": "bob"}` without a single quote or colon. A line that ends in a label (`Password:`, `Commit SHA:`) is judged together with the line right below it, for form fields under their labels and values that wrapped onto the next line.
   - **Evidence per category.** A provider prefix (`sk-`, `AKIA`, `ghp_`), a valid checksum or a field label is strong evidence. A long hex or base64 run is weak: it is a key unless its line calls it a commit, checksum or other hash, and a credential label still wins. A 6 to 8 digit number is a code only next to a security word ("code", "verification", "sign in") or alone on its line. "Order number: 482913" and "Downloads: 12345678" are not codes. A labelled password or token is covered whatever its length: `pwd=1234` counts, and so does `--password hunter2`. A password label may be misspelled, as typed or as OCR read it. `labels.py` compares labels in a folded view (case, accents, full-width forms, invisible characters, spaced-out letters and OCR look-alikes such as `pa55w0rd`), and a long label may be one edit off: `pasword`, `passwrod`, `DB_PASWORD`. Short labels like `pwd` stay exact, and `password_length` or `passwordField` name other fields. A label cut short (`passwor`) never takes a separator the detector only inferred, as it's likelier the start of a longer word OCR split. A security code with letters counts after its label (`Recovery code: abcd-efgh-ijkl`). A reference whose closing `)` OCR misread as `}`, `]` or `|` is still a reference. Quoted values are read to their closing quote, with escapes. An unquoted value after `=` ends at the next space or field (`pwd=1234;user=bob`). After `:` it can run to six words (`Password: correct horse battery staple`). References like `os.getenv("DB_PASSWORD")`, `${DB_PASSWORD}` or `settings.DB_PASSWORD` are not values. That holds through OCR's usual misreads, as long as the setting's `UPPER_SNAKE` name survives. A spell-check underline in Notes turned `os.getenv` into junk, but `("DB_PASSWORD")` was still readable. OCR can read the colon after a label as `"`, `;`, `..` or `.`, and those count as a colon. Curly quotes count as quotes. A phone is a North American number, any `+` number with 8 to 15 digits, or a labelled number in any format. Fake-looking numbers aren't excused. A card number in its printed groups or after a card label stays covered when one misread digit breaks the Luhn check. It is counted as `uncertain`. Long numbers in general are not cards.
   - **Values, not labels.** Each rule returns the value's span. Where OCR gives a box per word (Apple Vision, Windows OCR), only the value's words are covered and `password:` stays readable. A box for a whole line (RapidOCR) can't place the value's first character from the text, so there the cover still starts at the label.
   - **Careful rereads** (`--rescue-reads`, off by default). A newly read line can name a secret with no value read after it, or hold a card that fails its check. When that happens, the line and the space to its right are read again with Vision's accurate mode, about 25 ms a crop. Nearby lines are read as one crop, at most two crops a frame, within 150 ms of rereading a second. What it reads is added as a second reading beside the first and never clears a cover. Answers are kept for the exact pixels they read. A line also counts as in doubt when a junk word sits where a label would, before `:` or `=` (Notes' red spell-check underline turns a misspelled `passwrod:` into `RSIAI.wiod:`), when a word is two edits from a password label, or when it names a recovery or verification code. Rows in the crop that belong to the lines above and below are blanked, as cut-off neighbours made Vision misread the line itself. In a careful reread's words a password label may be two edits off (`Rasswrod:`), never in a fast read's, and real words such as `passport` never count. A cover found only in a careful reread takes 8 reads that find nothing, not 2, before it comes off, as the fast read never sees that value: two of its misses took the cover off mid-scroll and the next careful read put it back. Lines left over for lack of time wait, with the value after a garbled label covered meanwhile, and a still screen keeps scanning until each has had its reread. Marks on words, careful or waiting, move with a scroll or drag.
4. `covers.py` keeps one cover on each secret from its first sighting until it is really gone: its pixels changed and a new read found nothing there, it left the screen, or the same text turned up somewhere else. Time alone never ends a cover. Covers keep a hash of the text, never the text.

There are two OCR engines:

- **RapidOCR** (default) runs locally on both OSes. It returns lines, so a secret's box is estimated from where it sits in the line.
- **Apple Vision** (`--ocr apple`, macOS only) is much faster and gives real word positions, but finds fewer secrets than RapidOCR. It needs full Retina frames: at standard size it misses most small text. Vision reads one area at a time per process, so `read_ahead.py` starts reading changed areas in worker processes (`ocr_worker.py`) as soon as each frame is captured.

`find_emails.py`, `find_phone.py`, `find_cards.py` and `luhn.py` are standalone helpers. The pipeline doesn't call them.

## Known limits

Eclipse reduces risk. It doesn't guarantee that nothing leaks.

- OCR can miss text, and the rules don't recognize every token format.
- Covers can still fail on a live screen in cases we haven't pinned down yet.
- Video and big window changes need full scans, which take the longest.
- Phones without a `+` or a label are only found in North American format.
- A 6 to 8 digit number alone on its line still counts as a code, even when the line above says it's an order number. A 4 or 5 digit code is only caught next to a security word, so a bare 4-digit code is missed.
- A label and its value must be on the same line, or the value on the line right below. A field far to the right of its label isn't matched.
- One OCR word is covered whole. In `pwd=1234;user=bob`, read as one word, `user=bob` is covered too. Covers also take the compositor's padding, so in tightly spaced text the edge of the line above or below can be covered.
- At 10 pt Helvetica the fast read garbles some lines past recovery. `${DB_PASSWORD}` reads as `SIDB PASSWORD}` and is covered. On selected text, a JSON password loses every quote and colon and is missed.
- After `password:` an unquoted value runs up to six words, so a sentence after a label can be covered with it.
- A password label two or more edits off (`paswrd`) is only covered when a careful reread reads it so: a fast read garbling it asks for one, but a typed typo the careful read also sees as two edits off isn't covered.
- When Vision's fast read drops a misspelled label altogether, nothing asks for a careful read, so its value shows until the line is read again.
- At 10 pt in a proportional font, Vision's fast read can garble a label (`password.` for `password:`) and miss its value. `--rescue-reads` recovers this in the generated screens. It hasn't been measured live yet.
- Names, postal addresses and other personal details have no rule. The categories above are all that's detected.

## Testing

| Command | What it checks |
| --- | --- |
| `python -m pytest` | Unit tests |
| `python -m eval.run_eval` | Leaks and latency on the clips in `eval/clips`. Exits 1 if anything leaks. |
| `python -m eval.stress_60` | Hard screen activity at 60 fps through real Apple OCR, counting leaked pixels directly |
| `python -m eval.sustained_motion --seconds 60` | The whole pipeline over time, with failed reads, panic and resume, and new keywords. Uses fake OCR. |
| `python -m eval.scroll_compare` | How covers behave during a scripted scroll |
| `python -m eval.motion_flicker` | Window drags and scrolls through real Apple OCR: secret pixels left showing, and how much cover shapes change around their text from frame to frame. `--look-ahead 18` draws frames as the pipeline's look-ahead does. |
| `python -m eval.capture_bench` | Capture speed alone, per backend |
| `python -m eval.accuracy_scene --summary` | Fake secrets and harmless look-alikes in dark, light, selected and coloured themes, at 13 and 10 pt, in Menlo and Helvetica, through real Apple OCR. Reports secret glyphs still showing, harmless text covered, and black away from secrets. `--rescue` adds careful rereads. |
| `python -m eval.obs_path send`, then `verify` | Which frames really reach an OBS recording. `--plan` runs output paths back to back in one recording. |

Test clips and scenes use fake secrets only.
